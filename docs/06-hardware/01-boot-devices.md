## 跟着做：解释、预测、操作、观察


### 1. 把硬件启动与 systemd 接起来

```text
芯片启动机制 → 板级固件/引导程序 → Linux 内核与设备树
                                      ↓
                               根文件系统与 PID 1
                                      ↓
                                服务与应用程序
```

具体固件阶段、分区和镜像布局依板卡 BSP 而定；这张图只表达关系，不是通用刷机步骤。设备树描述平台硬件，驱动根据匹配信息管理设备并提供接口。用户程序不直接执行设备树。

### 2. 从当前运行系统找证据

```bash
uname -r
tr '\0' '\n' < /proc/device-tree/model
tr '\0' '\n' < /proc/device-tree/compatible
ls /sys/bus/platform/devices | head -n 15
```

设备树字符串通常用 NUL 分隔，所以用 tr 转为换行后阅读。设备树接口在部分系统不存在，应记录镜像及平台，不把缺失直接解释为板卡损坏。

### 3. 找到设备、驱动与用户接口的边界

```bash
ls -l /sys/class/thermal
ls -l /sys/class/video4linux
ls -l /dev/dri
```

某些路径不存在属于待调查事实。sysfs 常通过链接连接设备模型，`readlink -f` 可跟踪一个实际条目。`driver` 链接可反映已绑定驱动，但不保证所有用户空间运行库已安装。

**先预测：** 看到 compatible 中有 rk3576，是否就能运行任意 RKNN 模型？还缺模型目标、驱动、Runtime、库与权限等条件。

### 排错边界

设备描述不等于已绑定驱动；驱动存在不等于节点权限允许；节点存在不等于应用协议和模型格式匹配。按层记录证据，不要先修改设备树或更换内核。本主线不要求编写驱动或移植 BSP。

进一步阅读：[Linux sysfs 访问规则](https://docs.kernel.org/admin-guide/sysfs-rules.html)。关注依赖具体内核布局的接口变化。
